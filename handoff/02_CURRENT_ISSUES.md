## A：练习页/解析页状态识别

定位：`fenbi_crawler_v2.py` 的 `crawl_current_page`、`solution_visible`、`ensure_solution`。

现在先等 `.submit-btn` 或解析标记出现，再立即检查 `app-question-choice / .ti-content / [data-role=stem]` 是否可见。提交按钮可能先出现；题干可能仍异步加载；自定义元素可能 `display: contents` 导致父组件不可见、子内容可见。以上均是**待复现假设**，截图不能确定是哪一种。

接手建议：先保存并分析真实页面的可见渲染证据与加载阶段；建立有期限的页面状态等待。只在唯一的正常交卷入口及真实练习内容被确认后提交。增加“先有按钮、后有题干”“组件父元素无矩形但子内容可见”“解析延迟加载”的失败/修复回归，不要直接删除保护条件。

## B：独立总题数证据未识别

定位：`snapshot_dom.js` 的 counts/cards，以及 `extract_exam_data` 和 `bank_core.validate_exam`。

当前只从 `[data-question-count], .question-count, .total-count, .paper-summary` 解析部分“共 N 题”文字。历史用户资料提到真实答题卡显示过 `0/130`，但当前 B 卷的实际 DOM 和计数区没有取得。不能猜 B 卷必定 135，也不能用 `len(questions)` 放宽校验。

接手建议：从当前可见答题卡/题量文字取得独立证据，保留其原文、节点和来源；兼容经实际确认的 `已答数/总数` 或完整题卡等结构。多处证据冲突时待补。继续检查卡片题号到原始 ID 的关联，不能因抓到 135 个组件就认为题序无缺。

## C：重复读取和停止条件

定位：`extract_exam_data` 的 fingerprint、stagnant、click_next、滚动。

现在只在 `stagnant >= 3 AND not moved` 时退出；若页面不断滚动但没有新增题目，或“下一题”按钮一直可点且没有进展，会持续到阶段 90 秒或轮数上限。截图里重复 135 至少说明用户看不到有效进展，不能单凭截图断定发生永久死锁。

接手建议：基于题目内容变化、可见页/滚动位置变化和真实新增题目设置独立的无进展边界；不要只按采集数量判断，因为答案解析可能后加载。每次退出记录原因；保留题面与原始片段，并在总题数未知时明确待补。测试“按钮可点但不切换”“滚动有位移但题目内容不变”“题数不变但解析后加载”。
